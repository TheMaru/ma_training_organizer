# 01 — Seed ranks by their natural key, not by name

Status: ready-for-agent

`ensureRank` looks a rank up by its **name** before deciding whether to insert
it:

```sql
SELECT 1 FROM ranks WHERE grading_system_id = ? AND name = ?
```

The name is therefore the seed's idempotency key — and it is a display-shaped
string that nothing guarantees to be stable. Move the lookup onto the rank's
natural key, and let the seed correct a name it no longer agrees with.

## Why this is a latent bug

Respell `rankName` — say `White, 1 stripe` becomes `White I` — and the next
re-seed finds no match, **inserts a second rank**, and leaves every existing
promotion pointing at the old row. Two rows then mean the same thing, one
orphaned from new promotions and the other from the history. Nothing fails
loudly: the seed reports success.

The database does not catch it. There *is* a unique index on
`(grading_system_id, name)` — `ranks_system_name_idx`, added by migration
`00002` — but it guards a different failure: two rows sharing one name. The
rename produces two rows with *different* names for the same rank, which the
index permits by construction.

This is the same trap ADR-0006 removed for grading systems, where a translatable
`name` could not also be a URL key, and the fix was to move identity onto a
`slug`. Ranks never got the equivalent treatment.

## Decisions (triage, 2026-08-03)

**The lookup key is `(grading_system_id, rank_group, degree)`.** Both columns are
`NOT NULL` since migration `00002` and always set by the seed, and the triple
determines the name — `rankName` is a pure function of the last two. **No
migration, no new column, no new index.**

**No unique index on the natural key.** It was considered and rejected on
ADR-0001 grounds: migration `00002` states that `rank_group` and `degree` are
"empty/zero where a system defines no such dimension", so a future system with
named steps and no colour or degree axis would have every rank at `('', 0)` and
a unique index would admit exactly one of them. That would be a schema
constraint presupposing belts, inside a model whose stated purpose is
discipline-agnosticism — the line ADR-0004 was careful to keep on the view side.

The same objection touches the *lookup* in a weaker form, and is accepted
knowingly: for such a system the lookup would match the first rank and skip the
rest. The difference is that the lookup is **code**. The current seed structure
(`belts` × `maxDegree`) cannot express a non-belt system at all, so whoever adds
one is already rewriting `gradingSystemSeed` and will rewrite the lookup with it.
An index would survive that rewrite silently.

**A rank slug was rejected** as disproportionate: 77 slugs either hand-authored
or derived from group and degree, and deriving them reintroduces the emptiness
problem. The failure it guards against needs someone to deliberately respell a
string that, after [[i18n-domain-data]], is never displayed.

**On a hit, the seed updates the name.** If the found row's `name` differs from
what `rankName` now produces, it is corrected. This mirrors
`ensureGradingSystem` one function above, which already updates `sort_order` and
`slug` on its hit path so a re-seed repairs rows predating a migration. Leaving
the row untouched would only be half a fix: no duplicate, but the rename
silently ignored instead of silently duplicated.

**`sort_order` stays untouched on the hit path.** `ensureRank`'s existing
contract — a re-seed neither duplicates nor reorders — is a separate decision and
is not renegotiated here.

## Nothing to repair

Checked at triage. The development database holds 77 ranks, no rows with an empty
`rank_group`, and no duplicates on the natural key. The app has never been
deployed, so no other database exists. This ticket is **purely preventive**.

## Acceptance

- `ensureRank` looks up by `(grading_system_id, rank_group, degree)`.
- On a hit whose stored name differs from the freshly computed one, the name is
  updated; `sort_order` is not.
- On a miss, the insert is unchanged.
- Its doc comment is rewritten: the current one states that existing rows are
  left as-is, which stops being true.
- **Regression test:** seed, rewrite a rank's name directly in the database to
  simulate a respelling, re-seed, then assert both that no second row exists for
  that `(rank_group, degree)` and that the name has been corrected back. Prior
  art is `TestSeedIsIdempotent`, which already does the seed-twice dance.
- A test covering the unique-index collision: if two ranks were to converge on
  one name, the seed must fail loudly rather than corrupt quietly.
- `go test ./...` passes; `TestSeedIsIdempotent` and `TestSeedRanksOrderedWithMetadata` still pass unchanged.

## Comments

2026-08-03 — > *This was generated by AI during triage.*

Found while grilling [[i18n-domain-data]] 01, and filed separately on purpose.

That ticket localizes rank names in the view, which makes the stored English name
purely internal — a seed lookup key plus a fallback, never displayed. Discovering
that the one remaining job of that name rests on a respellable string is what
surfaced this. The two are independent, though: this bug predates i18n entirely
and would exist if the app were German-only. There is **no ordering constraint**
between them.

It was deliberately kept out of that ticket. Localizing names is a view-layer
change with no data risk; changing how reference data is seeded can duplicate
rows that promotions hang off, and deserves its own tests and its own review
rather than riding along with a display change.

**A correction to the record.** The first version of this ticket, and ADR-0009's
consequences section, both claimed there was no unique index behind the name
lookup. There is one — `ranks_system_name_idx` from migration `00002`, which the
initial analysis missed by reading only `00001`. Both have been corrected. The
bug is unaffected: the index prevents two rows sharing a name, and the rename
scenario produces two rows with different names.
