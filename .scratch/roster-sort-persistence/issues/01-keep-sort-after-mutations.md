# 01 — Mutations drop the trainer's active roster sort

Status: ready-for-agent

Deleting, creating or editing an athlete redirects to a bare `/athletes`, so the
trainer lands back in the default Vorname-ascending view. Found by the code review
of [[roster-sortable-columns]] (shipped in `c8ff458`, 2026-07-27).

## Motivation

`handleAthleteDelete`, `handleAthleteCreate` and `handleAthleteUpdate` all redirect
to `/athletes` without the sort parameters. Before sorting was generic this cost at
most a direction flip; now a trainer who sorted by "Aktueller Rang" to work through
a grading list loses their view on every delete. The delete button sits in the
roster itself, so it is the common case.

## Scope

The roster's sort state lives in the URL and stays there across every navigation
and mutation: links out of the roster carry `?sort=&dir=`, each handler reads them
from its own request, and each redirect appends them again.

## Resolved in triage (2026-07-27)

- **Where the sort comes from.** The **URL**, everywhere — not a hidden form field,
  not `Referer`, not `HX-Current-URL`, not session state. `Referer` is spoofable
  and optional; `HX-Current-URL` only exists on the HTMX path and would break
  without JavaScript. The URL is the one carrier that works on both the HTMX and
  the plain-form path, is shareable and bookmarkable, and cannot drift out of sync
  with what the trainer sees (ADR-0002, server-rendered, progressive enhancement).
- **Scope is all three mutations, plus the navigation links.** An earlier
  delete-only scope was rejected: it was only cheaper because it assumed a second
  mechanism (hidden fields) for the form pages. With the URL as the carrier there
  is one mechanism, so restricting it would create the inconsistency it was meant
  to avoid.
- **Whitelisting.** The redirect target is built from `store.NormalizeRosterSort`
  plus the two direction literals — never from the raw query parameter, so no
  user-controlled string reaches a `Location` header.
- **No new tracker field.** Category stays in the brief below rather than becoming
  a `Type:` line; `Status:` is the only role this tracker carries, and `Type:` is
  already taken by the wayfinder flow.

## Agent Brief

**Category:** enhancement
**Summary:** Carry the roster's `?sort=&dir=` state through every link out of the
roster and every mutation redirect, so a trainer's sort survives their work.

**Current behavior:**
The roster sorts server-side from `?sort=<col>&dir=<asc|desc>`, normalised through
`store.NormalizeRosterSort` (unknown values fall back to Vorname ascending). Those
parameters exist only while the trainer stays on the list. Every link out of the
roster (athlete detail, edit form, "Neuer Athlet") drops them, and the create,
update and delete handlers all redirect to a bare `/athletes` — so any mutation, and
any trip through a form, silently resets the view to the default sort.

**Desired behavior:**
The sort state is part of the URL for the whole round trip. Opening an athlete from
a sorted roster, editing them, creating a new one, or deleting one all return the
trainer to the same sorted view they started from. A request that arrives with an
unknown `sort` or an invalid `dir` still resolves to the default view, and the
redirect it produces carries the *normalised* values, never the raw input. Landing
on `/athletes` with no parameters at all keeps working exactly as today.

**Key interfaces:**
- The roster's header/view model (currently built by `rosterHeaders`) already knows
  the active column and direction — reuse that resolved state as the single source
  for building outgoing links, rather than re-reading the raw query in each spot.
- `store.NormalizeRosterSort` plus the `asc`/`desc` literals are the only permitted
  inputs to a redirect target or `Location` header.
- The shared `redirect` helper serves both the HTMX path (`HX-Redirect`) and the
  plain 303 path; whatever carries the sort must work identically on both, since
  the roster's delete button posts via HTMX but must still work without JavaScript.
- The athlete create/update/delete handlers each need the sort available from their
  own request to build their redirect target.

**Acceptance criteria:**
- [ ] Deleting an athlete from a roster sorted by any of the five columns, in either
      direction, returns to that same sorted view — on both the HTMX and the
      JavaScript-disabled path.
- [ ] Creating an athlete from a sorted roster returns to that sorted view.
- [ ] Updating an athlete reached from a sorted roster returns to that sorted view,
      and the edit form's cancel/"Zurück" link returns there too without saving.
- [ ] Opening an athlete's detail page from a sorted roster offers a way back to
      that same sorted view.
- [ ] A request with junk `sort`/`dir` values renders the default view, and any
      redirect it produces contains only whitelisted values (or none).
- [ ] `/athletes` with no query parameters behaves as it does today.
- [ ] Tests cover at least: delete-preserves-sort, junk-parameters-produce-a-safe
      redirect, and the existing roster sort tests still pass unchanged.

**Out of scope:**
- Changing the sort mechanism, the default column, the tie-break rules or the
  five sortable columns — this ticket only carries existing state around.
- Persisting the sort per trainer (session or database). The URL is the carrier;
  see the triage note above.
- The missing sort affordance at phone widths — that is
  [[roster-sort-on-mobile]].
- Pagination or filtering state ([[roster-cohort-filter]]).
