# 01 — Localized rank and grading-system names

Status: done

Localize the **domain data** shown to trainers — rank/belt names (`White`,
`White, 1 stripe`) and grading-system names (`BJJ Kids`) — so a German UI shows
`Weiß` / `Weiß, 1 Streifen` / `BJJ Kinder` rather than the raw English seed
strings.

Parked deliberately out of the UI-i18n feature ([[i18n-ui]]), which covers only
UI chrome + Go messages. Accepted interim state: UI is translated, but rank and
system names render as their raw (English) seed data.

## Why it is its own (bigger) concern

- Rank names are **data-driven** and are what a promotion targets (ADR-0001).
  Localizing them means per-locale translations in the model — `name_de`/`name_en`
  columns or a translation table on ranks and grading systems — a real model
  change, disproportionate to bundle into UI i18n.

## Likely subsumed by the belt visual

The belt graphic ([[rank-belt-visual]]) already plans to render a rank from
`rank_group` (colour) + `degree` (stripes) via a colour-name→something map. If
that map is **locale-aware** (colour → localized label), it produces a localized
rank *label* for free — so rank-name i18n may fall out of the belt-visual work
rather than needing per-rank translation columns. System names (`BJJ Kids`) are
not covered by that and would still need their own translation.

## Open questions (triage)

- Per-rank translation columns/table vs. a locale-aware colour+degree renderer
  (coordinate with [[rank-belt-visual]]).
- How to localize system names (`BJJ Kids` → `BJJ Kinder`) — translation column
  on `grading_systems`, or leave proper-noun-ish system names untranslated?
- Fallback when a translation is missing for the active locale.

2026-08-03 — > *This was generated by AI during triage.*

**Grilled and spec'd** (grill-with-docs). Every open question is resolved; full
detail in [`../spec.md`](../spec.md). Status → `ready-for-agent`.

**The shape.** Rank names are composed in the view from `rank_group` + `degree`,
never stored. Fifteen catalog keys per locale: nine colour words, five degree
patterns for degrees 1–5, one split pattern. Degree 0 is the colour word alone.
Grading-system names are one key per slug (`system.bjj-kids`), which ADR-0006
made the stable identity. English composes from the catalog too, because the
parity test forces both locales to carry the same keys — so the stored name is
never displayed on a resolved rank. **No schema change, no migration.**

**Decisions taken during the grill, beyond what the comment above had:**

- Degrees are *enumerated* rather than interpolated with `%d`, so pluralization
  lives in the catalog and not in a Go branch. The enumeration runs to 5, the
  bound the belt graphic already uses, because `seed.go` leaves the rare fifth
  BJJ stripe to clubs that need it.
- The split-belt joiner is a *pattern* (`%s-%s`) in the catalog, not a hardcoded
  hyphen. The `-` the parser splits on belongs to the stored data's format and
  has nothing to do with how translated colour words are joined — those are two
  separate decisions that only look alike.
- System names go in the catalog rather than a Go table beside `beltColours`.
  The line: hex values stay in Go because a fill is not language; human-readable
  text goes where this project keeps text, and gets the parity test for free.
- One fallback rule for everything — a catalog miss renders the stored English
  name, the rule ADR-0004 already set for an unresolvable colour. Needs
  `i18n.Lookup(locale, key) (string, bool)`, because `T` returns the key on a
  miss and `rank.degree.7` as an athlete's rank would be worse than the English.
- Composition happens in template funcs closing over the locale, with the logic
  in Go and signatures mirroring `belt`. `rosterLine.RankLabel()` stops being a
  method — it cannot reach the locale — and becomes a func over locale and row.

**Two surfaces the inventory above had missed.** It listed five *system*-name
sites; rank names were never inventoried separately. The promotion form renders
every rank of a system as an `<option>` — 77 of them — and that surface has no
belt graphic, which is what forces the label helper to exist independently of
`beltSVG`. Nine sites total, listed in the spec.

**Two display-only fields to add**, both denormalised exactly as the belt work
added `Group`/`Degree`, and both one column on a join that already exists:
`GradingSystem` gains its slug, `Promotion` gains its system slug. `RosterRow`,
the filter options and `store.Rank` already carry what they need.

**Sorting was checked and is safe.** `RosterSortRank` orders by
`system_order, rank_order`, never by name, so localized labels do not disturb it.

**Paper trail.** ADR-0009 records the decision plus the two facts it rests on
(`seed.rankName` is pure; only the seed writes ranks). ADR-0008 keeps its core
decision and gains a pointer marking its scope paragraph superseded in part.
`CONTEXT.md`'s `Rank` entry gained the identity/display-label line that
`GradingSystem` already carried.

**Spun out:** [[rank-seed-identity]] 01. `ensureRank` keys on the rank *name*
with no UNIQUE constraint behind it, so respelling `rankName` would silently
insert duplicate ranks while existing promotions point at the old rows. Found
here because this ticket makes the stored name purely internal, but it predates
i18n and carries real data risk, so it is not in this build.

**Seams for the build** (all existing, detail in the spec): rendered pages over
`httptest` for the nine surfaces in both languages — extending `mixedRoster`,
which today has only plain white and blue at degree 0 and so exercises neither a
degree pattern nor a split belt; the in-package test file beside `belt_test.go`
for the exhaustive colour × degree matrix and the fallbacks; and `internal/i18n`
for `Lookup`'s miss contract against the synthetic catalog pair. The seeded
colour groups get exported from `store` so this guard and the existing
`TestBeltSVGCoversEverySeededColour` stop keeping separate copies of the list.

2026-08-04 — > *This was generated by AI during implementation.*

**Built.** Rank and grading-system names are composed in the view from catalog
pieces; all nine surfaces render localized text in both languages. No schema
change, no migration.

- `i18n.Lookup(locale, key, args...) (string, bool)` beside `T`, so a miss can
  fall back to the stored name instead of rendering the key.
- Sixteen keys per locale after all: the spec's fifteen (nine colour words, five
  degree patterns, one split pattern) plus the two `system.<slug>` keys, which it
  counted separately.
- `belt.go`'s parse split out as `splitRankGroup`, returning colour *names*.
  `resolveBelt` and `rankLabel` share it, which is what makes "graphic and label
  degrade together" one definition rather than two lists.
- `rankLabel` / `systemLabel` / `rosterRankLabel` in `internal/web/ranklabel.go`,
  registered as template funcs closing over the locale. `rosterLine.RankLabel` is
  gone — a method cannot reach the locale.
- Plumbing: `store.GradingSystem.Slug`, `store.Promotion.SystemSlug`, both off
  joins that already existed. `store.SeededRankGroups()` exported; the belt
  coverage test dropped its hand-copied colour list onto it.

**Tests** at the three agreed seams: rendered pages in both languages
(`internal/web/i18n_domain_test.go`), the exhaustive colour × degree matrix and
the fallbacks in-package (`ranklabel_test.go`), and `Lookup`'s miss contract
against i18n's synthetic catalog pair. `mixedRoster` now promotes to
`Grey-White, 2 stripes` and `Blue, 1 stripe`, so the shared fixture exercises a
split belt and both stripe phrasings. Five existing German-page assertions were
updated from raw English to the composed labels.

**Two things the review changed.** A comment in `roster_test.go` still claimed the
chips carry raw seed names — deleted. And ADR-0009's bullet said the template funcs
take whole structs; the spec had since settled on `belt`-shaped scalar arguments
(three call sites carry a rank on three different types), so the ADR bullet was
corrected to match what shipped rather than the code silently contradicting it.

**Not done, as specified:** [[rank-seed-identity]] 01 — `ensureRank` still keys on
the rank name. `seed.rankName` now carries a comment saying why that name must stay
English.
