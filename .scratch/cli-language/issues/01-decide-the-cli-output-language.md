# 01 — Decide what language the CLI speaks

Status: ready-for-agent
Category: bug

The i18n spec states, as settled scope, that internal and developer-facing
output "stays English": `serverError`/500s, wrapped store/auth/config errors, and
**CLI output** — "Verified already clean". That verification was true when it was
written, and it is not true now.

`cmd/organizer/import.go`, added later by [[csv-athlete-import]], reports to the
trainer in German by design: `"%s importiert, %d übersprungen"`, `"… ist kein
gültiges Datum (JJJJ-MM-TT oder TT.MM.JJJJ)"`, `"Datei enthält keine
Kopfzeile"`, `"CSV-Format ungültig: %v"`. `main.go` even gained an
`errAlreadyReported` so that German report is not followed by an English
`error:` line. The `seed-demo` fixtures carry German prose too, though that is
sample content rather than UI.

So there are three positions and nobody has picked one:

1. **The CLI is a trainer-facing surface and stays German.** It is run by the
   same person who uses the web UI, on their own club's data; the import report
   is something they read, not a log line. Then the i18n spec's scope sentence is
   simply wrong and should be corrected — and the CSV column headers
   (`Vorname`/`Nachname`) already commit the file format to German anyway.
2. **The CLI is developer-facing and becomes English**, matching the spec. Means
   translating `import.go`'s report and error strings, and deciding whether the
   `-athletes` CSV headers follow (they should not — that is a file format, and
   changing it breaks every spreadsheet a club has already prepared).
3. **The CLI is bilingual too**, resolving from `LANG`/`LC_ALL` through the same
   `internal/i18n` catalogs. Technically cheap now that the catalogs exist, but it
   puts trainer-facing strings into a package whose scope ADR-0008 deliberately
   drew around the web UI.

## Why it matters at all

Not much, on its own — a German report in a German club is fine. It matters
because the spec now contains a false statement about the codebase, and the next
person to read it will either trust it or spend an hour finding out it is stale.

## Acceptance

Whichever position wins, `.scratch/i18n-ui/spec.md` gets corrected so its scope
section describes the code as it actually is.

## Agent Brief

**Category:** bug
**Summary:** Two documents assert that all CLI output is English; the athlete-import
subcommand is deliberately German. Correct the documents — the code is right.

**Current behavior:**
The i18n spec's scope section and ADR-0008's scope paragraph both state that CLI
output stays English, the spec adding "Verified already clean". The CSV import
subcommand reports to the trainer in German: the success report, the skipped-row
list, the abort report with its per-line problems, and the date-format,
missing-header, missing-column, duplicate-name and malformed-CSV messages.

Nothing about that is accidental, which is why the code is not what changes here.
Three separate constructions exist only to serve it: a helper that picks the
correct German noun form for a count (`1 Athlet` / `3 Athleten`), a German date
layout accepted alongside ISO on input, and a sentinel error in the command
dispatcher whose entire purpose is to suppress the generic English `error:` line
that would otherwise follow the German report. The decision was made during the
import work and simply never written down.

**Desired behavior:**
Both documents describe the CLI as it is: two surfaces, not one.

- **Trainer-facing** — the athlete-import subcommand is German, consistent with
  the German CSV column headers it reports on. Those headers are a file format
  clubs have already prepared spreadsheets against, and the error messages use
  the column names as their display names, so the two cannot diverge.
- **Operator-facing** — trainer creation, password reset, and the demo seed/clear
  subcommands stay English, along with `serverError`/500s and wrapped
  store/auth/config errors.

The spec's "Verified already clean" claim goes away rather than being restated:
it was a point-in-time observation, and it is what went stale.

**Key interfaces:**
No code changes. The two artifacts to correct are:

- The **i18n spec's "Scope: what gets translated"** section, specifically its
  "Stays English (internal/developer-facing)" bullet, plus the Acceptance bullet
  asserting "internal errors and CLI output remain English"
- **ADR-0008's scope paragraph** in its Decision section, which ends "and internal
  errors and CLI output stay English"

**Acceptance criteria:**
- [ ] Neither document claims that all CLI output is English
- [ ] Both distinguish the trainer-facing import subcommand (German) from the
      operator-facing subcommands (English), and both give the reason — the German
      CSV headers the import reports on
- [ ] The spec's "Verified already clean" phrasing is gone, not merely amended
- [ ] The spec's Acceptance section agrees with its own Scope section
- [ ] `git diff --stat` shows only `.md` files touched
- [ ] `go test ./...` passes, confirming no code moved

**Out of scope:**
- **Any change to the CLI's strings.** Translating the import report to English is
  the position this triage rejected: the messages embed the German column names as
  display names, so a half-translated report (`"Vorname missing"`) is worse than
  either pole.
- **A bilingual CLI via `LANG`/`LC_ALL`.** Also rejected. ADR-0008 deliberately
  binds locale resolution to the trainer's account and warns against a second
  mechanism; the CLI has no login and no account, so this would be exactly that.
  Nobody has asked for an English import report.
- **The CSV column headers.** They are a file format, not UI.
- **The German demo fixtures.** Sample content.
- **Rank and grading-system names.** Separate parked concern, [[i18n-domain-data]].
